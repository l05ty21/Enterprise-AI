## 一、项目简介

### 30 秒版
「智企协同是一个面向中小企业的 AI SaaS 平台。把账号权限、组织架构、工单、审批、企业知识库问答和 AI 助手放在同一套系统里，按企业租户隔离数据。技术上是 Vue3 + FastAPI，已部署在阿里云，并用 GitHub Actions 做前后端自动化发布。」

### 展开讲
| 维度 | 内容 |
| --- | --- |
| 项目名称 | 智企协同 / Enterprise AI |
| 形态 | B2B SaaS（多租户） |
| 当前能力 | 登录与 RBAC、部门树、工单流转、多级审批、知识库 RAG、流式 AI 对话、站内通知、待办工作台 |
| 代码托管 | Gitee（服务器拉代码）+ GitHub（触发 CI/CD） |
| 线上环境 | 阿里云轻量服务器（约 2 核 1G）Docker Compose 部署 |
| 演示账号 | 企业编码 `demo` / 用户名 `admin` / 密码 `Admin@123456` |

### 可展示页面顺序
登录 → 工作台待办 → 工单/审批 → 知识库 → AI 助手 → 说明 Actions 自动部署。

## 二、项目背景与解决的痛点

### 30 秒版
「中小企业常见三个痛点：权限和流程靠表格或微信传；制度文档散落找不到；想接大模型又不会接、也管不好成本和权限。我们用一套可多租户隔离的平台，把协同流程和 AI 问答合在一起。」

### 痛点 → 方案对照

| 痛点 | 传统做法 | 本项目怎么解 |
| --- | --- | --- |
| 账号权限混乱 | 共用账号、Excel 管人 | RBAC（角色/权限点）+ 企业租户隔离 |
| 报修/报销靠微信 | 消息淹没、无闭环 | 工单指派流转 + 多级审批 + 附件 |
| 制度/FAQ 问人 | 重复答、新人上手慢 | 知识库上传 → 切片向量化 → RAG 引用回答 |
| 接 AI 成本高、难统一 | 各业务直接调厂商 API | AI 模型网关统一接入多厂商 |
| 小服务器发版痛苦 | 本机构建、手工上传易错 | GitHub Actions 云端构建 + SSH 自动部署 |

### 目标用户
- 中小企业管理者 / IT 行政：管组织、权限、审批规则  
- 普通员工：提工单、走审批、问内部知识  
- 后续可扩：有私有化、合规要求的客户

## 三、核心功能与亮点

### 30 秒版
「亮点不只是 CRUD，而是：多租户隔离、统一 AI 网关、知识库带引用的 RAG、多级串签审批，以及在 1G 小机器上仍能落地的自动化部署方案。」

### 功能清单（按演示优先级）

1. **身份与权限**  
   JWT 双令牌、Argon2 密码、38 权限点 / 4 角色；接口级鉴权，前端隐藏不算安全边界。

2. **组织架构**  
   部门树、用户角色分配、跨企业数据隔离（测到 A 企业访问 B 返回 404）。

3. **工作台（我的待办）**  
   待我处理工单、待我审批、快捷入口——从「项目进度看板」改成「员工打开就有事可做」。

4. **工单**  
   提交 / 指派 / 状态流转 / 评论 / 附件；指派与评论触发站内通知。

5. **审批**  
   发起时可选手动选 1～N 审批人串签；通过进入下一级，驳回终结；支持附件。

6. **知识库 RAG**  
   上传文档 → 切片 → 向量化 → 混合检索 → 对话带引用。

7. **AI 助手**  
   流式输出；可挂接企业知识库问答。

8. **站内通知**  
   顶栏铃铛、未读数；工单指派、审批到达、通过/驳回会通知。

9. **工程化亮点**  
   分层清晰（api → service → repository）；90+ 自动化测试；Alembic 迁移；GitHub Actions CI/CD。

### 答辩时可强调的「产品改进」
曾从用户视角补齐：待办工作台、附件、多级审批、通知、强制改密与演示账号开关——说明不是只堆技术，也在打磨可用性。

## 四、核心技术栈与架构

### 30 秒版
「前端 Vue3 + TypeScript + Element Plus；后端 FastAPI + SQLAlchemy 异步；MySQL + Redis；AI 走自研网关；部署 Docker Compose；发布用 GitHub Actions。」

### 技术栈表

| 层级 | 技术 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Pinia、ECharts（工作台曾用） |
| 后端 | FastAPI、Pydantic v2、SQLAlchemy 2.0 Async、Alembic |
| 数据 | MySQL 8、Redis（令牌黑名单等） |
| AI | 多厂商兼容网关、Embedding + 混合检索 RAG（MySQL 向量方案） |
| 部署 | Docker Compose、Nginx、阿里云轻量服务器 |
| CI/CD | GitHub Actions（构建前端 + SSH 部署）+ Gitee（服务器拉代码） |
| 质量 | pytest（后端 90+ 用例）、租户隔离专项测试 |

### 架构分层（口述）

```
浏览器 Vue SPA
    ↓ HTTPS / JSON
API 路由（参数、权限声明）
    ↓
Service（业务规则、事务）
    ↓
Repository（SQL）
    ↓
MySQL / Redis / 本地上传目录
```

### 安全设计三点（加分）
1. **租户隔离**：`organization_id` 来自登录态，不信前端传参。  
2. **权限前后端双检**：菜单可藏，接口必须 `require_permissions`。  
3. **令牌**：access + refresh，退出吊销；密码 Argon2id。

## 六、CI/CD 自动化部署落地（重难点）

### 1. 流程说明

#### 日常发版（本机）

```powershell
git add .
git commit -m "说明改动"
git push github main    # 触发 GitHub Actions
git push origin main    # 同步 Gitee，供服务器拉取
```

#### Actions 流水线在做什么

```
push 到 GitHub main
  → checkout
  → Node 20：npm ci + npm run build（前端）
  → 私钥 Base64 解码，配置 SSH
  → scp 上传 dist 到服务器 /opt/enterprise-ai/deploy/html
  → ssh 执行 deploy/deploy.sh
       → git fetch Gitee
       → 有后端变更则 docker compose build backend
       → 健康检查 /api/v1/health，失败回滚
```

#### 分工一句话
- **GitHub**：跑流水线、构建前端、SSH 部署  
- **Gitee**：服务器拉代码（网络稳）  
- **阿里云**：跑 Docker 服务  

#### 相关位置
- 流水线：`.github/workflows/deploy.yml`  
- 服务器脚本：`deploy/deploy.sh`  
- 教学文档：`docs/github-actions-deploy-guide.md`  
- 监控：GitHub → Actions →「部署至阿里云」绿勾  

### 2. 真实踩坑与解决方案（答辩加分项）

| 坑 | 现象 | 根因 | 解决 |
| --- | --- | --- | --- |
| 1G 内存构建前端 | 服务器 build OOM / 极卡 | 内存不够 | **禁止服务器 vite build**；Actions 或本机构建后上传 `deploy/html` |
| Actions SSH 失败 | `ssh: 未找到密钥` | Secret 填成命令，或私钥粘贴丢换行 | Secret 存 **Base64**，流水线 `base64 -d` 再连 |
| 推 GitHub 重置 | `Connection was reset` | 国内访问 GitHub 不稳 | SSH 远程、代理、或热点；临时用 `deploy_frontend.py` + 推 Gitee |
| 服务器拉 GitHub | 超时 / `curl 52` | 云主机到 GitHub 不通 | 服务器 `origin` **只指向 Gitee** |
| 双远程不同步 | Actions 绿了后端仍旧 | 只推了 GitHub 没推 Gitee | 习惯 **两个都 push** |
| non-fast-forward | push 被拒 | 远程有本地没有的提交 | `git pull --rebase` 再 push |
| 定时器与 Actions 冲突 | 两边同时部署 | 旧 `ea-deploy.timer` 仍开着 | `systemctl disable --now ea-deploy.timer` |
| admin 改配置 | Permission denied | 目录属 root | 加 `sudo` |
| 密码「输不进去」 | 终端无回显 | Linux 安全设计 | 盲打回车；或用 `sudo` |
| 用户名写错 | fetch 失败 | `l0sty21` 写成 0 | 确认 `l05ty21`（数字 5） |

### 口述加分句
「CI/CD 的难点不在 YAML 本身，而在小规格机器、国内外网络差异和密钥安全。我们用『云端构建 + Gitee 拉码 + Secrets 托管密钥』把真实约束吃进去了，而不是只在本机演示脚本。」

### 可选现场演示（定时器）
1. `sudo systemctl enable --now ea-deploy.timer`  
2. `sudo tail -f /var/log/ea-deploy.log`（无新提交则静默；有提交才打日志）  
3. 演示完：`sudo systemctl disable --now ea-deploy.timer`  
说明：早期用定时器轮询 Gitee；现主力是 GitHub Actions，定时器仅作对比演示。

## 八、答辩高频 Q&A 话术准备

### Q1：和直接用 ChatGPT / 扣子有什么区别？
「通用聊天没有企业权限边界和流程闭环。我们把问答建在租户隔离和工单审批之上，答案可引用内部制度，AI 最终要能在权限内办事，而不是公网闲聊。」

### Q2：多租户怎么保证隔离？
「每张业务表带 organization_id；查询条件强制带当前登录企业；令牌里写入 org，不信前端传参；测试里验证跨企业访问返回 404，避免探测资源是否存在。」

### Q3：为什么知识库不用 Milvus？
「小规格机器跑不动完整向量库。现阶段用 MySQL 存向量 + 混合检索，先把 RAG 链路跑通；客户升配后再切专用向量库，网关和业务层已留扩展。」

### Q4：1G 服务器怎么做自动部署？
「前端绝不在服务器构建，改到 GitHub Actions；产物 scp 到 html 目录挂载。后端用已有 docker compose 脚本增量构建。用双远程避开云主机访问 GitHub 不稳定的问题。」

### Q5：密钥会不会泄露？
「私钥不进 Git；放在 GitHub Secrets；用 Base64 避免粘贴损坏；服务器只放公钥。仓库与 Actions 日志不打印密钥内容。」

### Q6：若 GitHub 推不上去怎么办？
「可改 SSH 远程或代理；紧急时推 Gitee + 本机 `deploy_frontend.py` 上传前端，保证演示可上线，网络恢复后再补推 GitHub。」

### Q7：测试覆盖怎么样？
「后端 pytest，含认证、权限、工单、审批、知识库、租户隔离及产品五件套（附件、多级审批、通知、强制改密等），总数 90+ 量级，保证重构和发版有底。」

### Q8：最大技术难点是什么？
「两块：一是企业级权限与租户模型要做对；二是在资源与网络约束下把 CI/CD 做成可重复的真实链路，而不是只在文档里写『自动化』。」

### Q9：下一步最想做什么？
「AI Agent：让助手直接查我的待办、创建工单、发起审批，并从『能问』升级到『能办』；同时接钉钉企微，降低推广阻力。」

### Q10：如何证明有商业价值？
「对内降沟通与培训成本；对外可按席位订阅 + 私有化。后续用数据看板展示工单处理时长、审批效率、AI 采纳率，用数据证明 ROI。」

### Q11：和你们课设里别的项目比，差异点？
「不是单页 Demo，而是：多模块业务闭环 + 安全模型 + 云上真实部署 + 可讲清楚的 CI/CD 踩坑与取舍。」

### Q12：定时器和 Actions 为什么不同时开？
「两套都会拉代码、发版，容易互相覆盖、难排查。演示完定时器后关掉，日常只保留 Actions 一条主链路。」
